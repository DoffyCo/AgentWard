# **AgentWard v3:**

AgentWard is a proof of concept security gateway for autonomous healthcare AI agents. The project is designed to analyze activity records generated by the ADOP testbed and identify actions that may violate healthcare-oriented security policies.

The goal of AgentWard is to provide an additional security layer around autonomous agents by examining agent requests, tool calls, resource access, data destinations, external sources, and patterns of tool usage. AgentWard is intended to complement existing authorization mechanisms such as role based access control (RBAC) by evaluating recorded agent activity against defined security policies.

AI tools were used during the development of AgentWard to assist with refining code, improving wording, and troubleshooting implementation issues. The overall project design, security concepts, policy definitions, and implementation decisions were developed and reviewed by the group.

### **Project Status:**

**Version:** v3

**Status:** Proof of Concept

AgentWard v3 is a decision support prototype. It does not directly control an autonomous agent or block tool calls in real time. Instead, it analyzes recorded ADOP activity and produces a security assessment based on seven defined security policies.

AgentWard operates as a manually initiated, observe only analysis tool. The stakeholder selects an ADOP JSONL file, reviews the generated security assessment, determines how individual alerts should be handled, and saves the assessment for documentation and auditing purposes.

The v3 PoC includes expanded policy detection, grouped alerts, updated risk scoring, potential source relationships, stakeholder audit reporting, and SHA-256 integrity verification.

### **What AgentWard v3 Does:**

##### AgentWard v3 currently performs six main functions:

1. **Reads ADOP records:**

   * Accepts ADOP JSONL activity records as input.
   * Supports reference clean and poisoned ADOP scenarios as well as previously recorded live ADOP sessions.
   * Extracts information such as the session ID, task ID, server, tool, arguments, target resource, result status, timestamp, sequence number, and scenario.

2. **Evaluates activity against policies:**

   * Compares recorded agent actions against seven healthcare oriented security policies.
   * Identifies potential resource boundary violations, unapproved data destinations, sensitive resource access, unapproved external sources, restricted information persistence, unapproved software dependencies, and excessive tool usage.
   * Considers recorded tool arguments and execution status when evaluating activity.
   * Assigns a severity level and provides a reason for each policy finding.

3. **Groups alerts and calculates risk:**

   * Combines multiple policy matches associated with the same ADOP record.
   * Groups related findings based on matching session, task, server, tool, and recorded target information.
   * Preserves individual event details and applicable policy matches within each grouped alert.
   * Calculates cumulative heuristic risk points and determines the overall risk band.
   * Ranks alerts to help stakeholders prioritize their review.

4. **Examines provenance and potential source relationships:**

   * Assigns a provenance flag indicating whether an alert can be traced to the associated ADOP event fields.
   * Examines earlier successful unapproved external fetches within the same session and task to identify potential source relationships with subsequent policy findings.
   * Displays sequence numbers, timestamps, and source URLs to support stakeholder review.
   * Distinguishes potential source relationships from confirmed causation or malicious activity.

5. **Provides a stakeholder dashboard:**

   * Presents the security assessment through a Streamlit dashboard.
   * Displays the overall risk band, heuristic risk points, grouped alerts, flagged events, and records analyzed.
   * Allows stakeholders to inspect ranked alerts, individual event details, provenance flags, and potential source relationships.
   * Allows stakeholders to record a disposition and optional rationale for each alert.

6. **Generates security assessments and audit reports:**

   * Produces human readable security assessment reports through the command line interface and stakeholder dashboard.
   * Includes reviewer information, review timestamps, stakeholder dispositions, and rationales in reports saved through the dashboard.
   * Records the SHA-256 hash of the original input file in the audit report.
   * Generates a separate SHA-256 checksum file for verifying the integrity of the saved audit report.
   * Allows stakeholders to save and download the assessment and its associated checksum.

### **Security Policies:**

##### AgentWard v3 uses seven security policies:

###### **AW-001 - Approved Resource Boundary:**

This policy identifies attempts to access or operate on resources outside the agent's approved resource boundary.

AgentWard examines recorded tool arguments and resolves resource paths relative to the appropriate ADOP directory. This allows the policy to identify boundary violations that may not be apparent from the recorded target resource alone.

The policy also examines Git operations for paths and arguments that may allow activity outside the approved repository.

Examples:

```text
../data/secret-outside-sandbox.txt
```

```text
--output=../data/exfiltrated-diff.txt
```

A successful operation outside the approved resource boundary receives a higher severity than an unsuccessful or blocked attempt.

An operation outside the expected working boundary can indicate an attempt to access or modify information that the agent was not intended to use.

###### **AW-002 - Approved Data Destinations:**

This policy examines destinations to which the agent attempts to write or persist information.

AgentWard evaluates destinations associated with filesystem writes, Git output operations, and memory storage. The policy checks whether these destinations are within the approved resource boundary or belong to an approved memory namespace.

Examples include:

* Writing a file outside the approved repository.
* Redirecting Git output to an unapproved location.
* Storing information in an unapproved memory namespace.

Successful operations involving established destination violations receive a higher severity than unsuccessful or unresolved operations.

External fetch operations are not treated as outbound data transfers under AW-002. External source trust is evaluated separately under AW-004.

###### **AW-003 - Sensitive Resource Access:**

This policy identifies access to resources that have been explicitly classified as sensitive or require additional authorization review.

Rather than identifying sensitive resources based on keywords in filenames, AgentWard uses the resource classifications defined in the ADOP testbed's `resource-tags.json` file.

The resource classifications include information such as:

* Resource path.
* Resource classification tags.
* Whether prior approval is required.
* Approved actors.

Examples of classified resources in the ADOP testbed include:

```text
data/customer_sample.csv
.env.example
```

A successful operation involving a resource that requires prior approval receives a higher severity than an unsuccessful operation.

Resources that are classified but do not require prior approval may produce a low severity informational finding.

###### **AW-004 - Approved External Sources:**

This policy identifies attempts to retrieve information from external sources that are not included in the approved-source configuration.

AgentWard examines the URL contained in the recorded fetch arguments and compares it against the configured approved external sources.

An unapproved source may contain untrusted instructions, misleading information, or content intended to influence subsequent agent actions.

Examples include:

* Retrieving a document from an unapproved external URL.
* Retrieving an unvetted software dependency README.
* Retrieving content from an unapproved URL on an otherwise familiar domain.

Unapproved external fetches receive medium severity findings.

The policy identifies a source requiring trust review. It does not independently determine whether the source contains malicious instructions or whether information was transferred out of the environment.

###### **AW-005 - Restricted Information Persistence:**

This policy identifies potential persistence of restricted information in agent memory.

AgentWard examines memory write operations and compares the recorded memory value against information returned by earlier successful resource reads within the same session and task.

Restricted resources include:

* Resources outside the approved repository boundary.
* Resources explicitly classified through the ADOP resource tags.
* Resources within configured restricted source directories.

The policy uses recorded sequence numbers to determine whether the resource read occurred before the memory write.

Recorded content is normalized to account for whitespace differences. A minimum matching length of 80 characters is used to reduce findings caused by short or coincidental matches.

Examples include:

* Reading restricted source code and subsequently storing matching content in memory.
* Reading a resource outside the approved boundary and subsequently storing matching information in memory.

A successful memory write containing matching restricted information receives a higher severity than an unsuccessful write.

The policy relies on the recorded content available in ADOP telemetry. It does not provide complete data lineage or detect every possible transformation of restricted information.

###### **AW-006 - Approved Software Dependencies:**

This policy identifies operations involving software dependencies that are not included in the approved dependency configuration.

AgentWard examines recorded writes to the repository's `package.json` file and compares dependency names and version specifications against the configured approved dependencies.

The policy examines the following dependency sections:

* dependencies
* devDependencies
* optionalDependencies
* peerDependencies

The policy also examines related Git staging and commit operations to identify potential progression of an unapproved dependency modification.

Examples include:

* Adding an unapproved dependency to `package.json`.
* Changing an approved dependency to an unapproved version specification.
* Staging a manifest containing an identified unapproved dependency.
* Committing a previously staged manifest containing an identified unapproved dependency.

AgentWard uses earlier recorded operations within the same session and task to establish relationships between manifest writes, staging operations, and commits.

Successful operations involving established dependency violations receive a higher severity than unsuccessful or unresolved operations.

The approved dependency configuration is based on the ADOP testbed's expected dependencies. An approved dependency is not necessarily free of vulnerabilities, and an unapproved dependency is not necessarily malicious.

###### **AW-007 - Excessive Tool Usage:**

This policy identifies patterns of excessive or repetitive tool usage that may indicate abnormal agent behavior, inefficient execution, or potential resource exhaustion.

AgentWard examines tool activity within the same session and task using recorded sequence numbers.

The policy evaluates three types of activity:

* Total tool calls within a task.
* Repeated tool calls with matching server, tool, and arguments.
* Consecutive failed retries of the same operation.

The current thresholds are:

| Activity | Medium Severity | High Severity |
|---|---:|---:|
| Total tool calls within a task | 15 | 30 |
| Repeated identical tool calls | 5 | 10 |
| Consecutive failed retries | 3 | 6 |

Findings are generated when the configured thresholds are reached. When multiple thresholds are reached by the same event, the highest applicable severity is used.

These thresholds are project-defined values informed by observations of the available ADOP corpus. They are not universal limits for autonomous agent activity.

The policy identifies patterns requiring stakeholder review rather than confirming that a denial-of-service attack has occurred.

### **ADOP Integration:**

AgentWard v3 uses activity records produced by the ADOP testbed rather than modifying ADOP itself.

AgentWard operates using the Static analysis approach. The stakeholder manually selects an existing ADOP JSONL file, and AgentWard evaluates the recorded activity.

The input may consist of reference ADOP sessions or previously generated live ADOP sessions. Analyzing previously generated live telemetry does not mean AgentWard is operating in Live mode.

The Static approach was selected because the current PoC focuses on evaluating recorded activity, producing decision-support assessments, and allowing stakeholders to review findings without modifying the ADOP execution environment.

For example, an ADOP record may contain information such as:

```json
{
    "session_id": "example-session",
    "server": "filesystem",
    "tool_name": "read_text_file",
    "arguments": {
        "path": "../data/example.txt"
    },
    "target_resource": "../data/example.txt",
    "result_status": "error",
    "scenario_tag": "poisoned",
    "task_id": "task-example",
    "seq": 1,
    "timestamp": "2026-08-12T13:20:34Z"
}
```

AgentWard uses the recorded information to determine whether the action requires security review.

The policy evaluation considers information such as:

* The tool and server associated with the operation.
* The actual arguments supplied to the tool.
* The requested resource or destination.
* Whether the operation succeeded, failed, or was blocked.
* Earlier related activity within the same session and task.
* Configured resource classifications and approved policy values.

AgentWard does not use the clean or poisoned scenario label as a condition for generating policy findings. The scenario label is included in the assessment to provide context for the selected input.

ADOP annotations can be used during evaluation to help understand the recorded activity, but they are not used as the basis for AgentWard's policy detection.

AgentWard also uses the ADOP testbed's repository structure and `resource-tags.json` file to support resource boundary evaluation and sensitive resource classification.

This approach allows AgentWard to operate as an external analysis layer without modifying the ADOP architecture.

### **Stakeholder UI:**

AgentWard v3 includes a Streamlit dashboard that presents the decision support assessment through a stakeholder facing interface.

The primary stakeholder is a security analyst or reviewer responsible for examining recorded autonomous agent activity and determining whether identified findings require additional investigation.

The stakeholder can upload an ADOP JSONL file, review the overall heuristic risk band and score, inspect ranked alerts, examine individual event details and potential source relationships, and record a disposition with an optional rationale.

#### **Launching the Dashboard:**

From the AgentWard project directory, install Streamlit if it is not already installed:

```bash
python -m pip install streamlit
```

Start the dashboard:

```bash
python -m streamlit run ui.py
```

Streamlit opens the dashboard in a browser.

The dashboard is normally available at:

```text
http://127.0.0.1:8501
```

Upload an ADOP `.jsonl` file when prompted.

The dashboard can be tested using the reference clean and poisoned ADOP sessions or previously generated live ADOP sessions.

#### **Stakeholder Review:**

The dashboard displays:

* Overall risk band and heuristic risk points.
* Number of grouped alerts.
* Number of flagged events.
* Number of records analyzed.
* ADOP session ID and scenario.
* Ranked alerts, including severity, applicable policies, task, target, and alert points.
* Number of occurrences associated with each grouped alert.
* Individual event sequence numbers, timestamps, execution status, and reasons.
* Provenance flags and an explanation of event traceability.
* Potential relationships between earlier unapproved external fetches and subsequent policy findings.
* Stakeholder dispositions and optional rationales.

The stakeholder can assign one of three dispositions to each grouped alert:

* **Needs review:** The finding requires additional examination before a decision can be made.
* **Escalate:** The finding warrants additional investigation or escalation.
* **Dismiss:** The stakeholder determines that the finding does not currently require further investigation.

The disposition represents the stakeholder's decision regarding the alert. It does not change the original policy finding, severity, or risk score.

AgentWard does not automatically enforce the stakeholder's decision or perform remediation.

#### **Dashboard Security:**

The Streamlit configuration restricts the dashboard to the local machine by binding the server to `127.0.0.1`.

The configuration is stored in:

```text
.streamlit/config.toml
```

```toml
[server]
address = "127.0.0.1"
```

Recorded values such as resource paths, task identifiers, tool names, and external URLs are displayed as plain text where applicable.

This reduces the risk of untrusted telemetry being interpreted as formatted Markdown or clickable links within the dashboard.

These controls reduce unnecessary network exposure and unintended interaction with untrusted content. They do not provide stakeholder authentication or complete protection against malicious input.

### **Report Integrity Verification:**

AgentWard v3 uses SHA-256 hashing to support the integrity and traceability of saved audit reports.

Two separate hashes are used:

* **Input SHA-256:** Identifies the exact input file analyzed by AgentWard. This hash is included in the saved audit report.
* **Report SHA-256:** Identifies the exact bytes of the saved audit report. This hash is stored in a separate `.sha256` checksum file.

The stakeholder can independently calculate the hash of a saved report and compare it against the generated checksum.

#### **Verify the Original Input File:**

Windows PowerShell:

```powershell
Get-FileHash "<path-to-input.jsonl>" -Algorithm SHA256
```

Linux:

```bash
sha256sum "<path-to-input.jsonl>"
```

Compare the calculated hash against the Input SHA-256 value recorded in the audit report.

Matching values indicate that the selected input file matches the bytes identified in the audit report.

#### **Verify a Saved Audit Report:**

Windows PowerShell:

```powershell
$report = Get-Item "<path-to-saved-report.txt>"

(Get-FileHash $report.FullName -Algorithm SHA256).Hash -eq ((Get-Content ($report.FullName + ".sha256")) -split "\s+")[0]
```

Expected output for an unchanged report with a matching checksum:

```text
True
```

Linux:

Navigate to the directory containing the saved report and checksum file.

```bash
sha256sum -c "<report-filename.txt.sha256>"
```

Expected output:

```text
<report-filename.txt>: OK
```

If the report is modified without updating its checksum, the calculated hash will no longer match the original checksum.

The integrity verification feature supports stakeholder accountability and the identification of changes to saved reports when compared against a trusted checksum.

Checksums help verify report integrity but do not provide authentication or prevent tampering. A person with access to both the report and checksum file could modify both.

The checksum mechanism does not provide encryption, digital signatures, or tamper proof storage.

### **Risk Scoring and Report Interpretation:**

AgentWard v3 reports ranked grouped alerts, heuristic risk points, an overall risk band, event traceability provenance flags, and potential source relationships.

These are transparent, project defined conventions. The project requirements call for decision support output but do not prescribe their formulas.

#### **Combined Policy Findings:**

Multiple policy matches associated with the same ADOP record are combined into one event-level finding.

The finding retains the applicable policy IDs and reasons and receives the severity associated with the highest matched policy severity.

For example, a Git operation that writes output outside the approved repository may match both:

* AW-001 - Approved Resource Boundary
* AW-002 - Approved Data Destinations

The operation is represented as one event level finding containing both policy matches rather than two independent alerts.

#### **Grouped Alerts:**

Related event level findings are grouped when they contain matching values for:

* Session ID.
* Task ID.
* Server.
* Tool.
* Recorded target resource.

Each grouped alert retains the individual events, applicable policies, reasons, and occurrence count.

The highest severity among the grouped events determines the severity and risk points assigned to the grouped alert.

Findings with incomplete grouping identifiers remain separate.

Grouping reduces repetitive alerts while preserving the underlying event evidence for stakeholder review.

Grouping does not remove the original ADOP records or establish that differently recorded targets represent the same resource.

#### **Risk Points:**

AgentWard uses the following risk point values:

| Severity | Risk Points |
|---|---:|
| High | 30 |
| Medium | 15 |
| Low | 5 |

Each grouped alert contributes risk points once, based on its highest severity.

The total heuristic risk score is the uncapped cumulative sum of the points assigned to all grouped alerts.

For example:

```text
7 High alerts x 30 points = 210 points
2 Medium alerts x 15 points = 30 points

Total heuristic risk score = 240 points
```

The risk score is not limited to 100 points.

#### **Risk Band:**

The overall risk band is determined by the highest severity present among the grouped alerts.

* **High:** At least one high-severity alert is present.
* **Medium:** At least one medium-severity alert is present and no high-severity alerts are present.
* **Low:** Only low-severity alerts are present, or no findings were detected.

The cumulative risk score and overall risk band serve different purposes.

The cumulative risk score represents the total project-defined risk points associated with the grouped alerts. The risk band identifies the highest severity requiring stakeholder attention.

A large number of medium-severity alerts does not automatically change the overall risk band to High.

#### **Ranked Alerts:**

Grouped alerts are ordered by:

1. Risk points in descending order.
2. Task ID.
3. Recorded target resource.

Because the risk points are determined by severity, high-severity alerts are presented before medium-severity and low-severity alerts.

Risk points and bands are triage aids only. They are not calibrated risk measurements, probabilities, CVSS scores, or proof of compromise.

### **Provenance and Potential Source Relationships:**

AgentWard v3 provides two forms of provenance-related information to support stakeholder review.

#### **Event Traceability:**

AgentWard assigns one of two provenance flags:

* **TRACEABLE:** The finding contains the session ID, task ID, server, tool, and recorded target resource needed to associate it with the corresponding ADOP activity.
* **INCOMPLETE:** One or more of the required event identifiers are missing or incomplete.

The provenance flag identifies event traceability. It does not establish the authenticity of the telemetry, the origin of the recorded information, maliciousness, or proof that PHI was disclosed.

#### **Potential Source Relationships:**

AgentWard examines earlier successful unapproved external fetches to identify potential relationships with subsequent policy findings.

A potential source relationship requires:

* Matching session ID.
* Matching task ID.
* An earlier successful external fetch.
* An external URL that is not included in the approved-source configuration.
* Valid sequence information establishing that the fetch occurred before the subsequent finding.
* A subsequent finding associated with AW-001, AW-002, AW-003, AW-005, or AW-006.

When the conditions are met, AgentWard includes the earlier fetch's sequence number, timestamp, and URL in the finding.

Example:

```text
Sequence: 12
Execution status: success
Policies: AW-001, AW-002

Potential source relationship (same session and task):
    Earlier successful fetch: sequence 11
```

Multiple qualifying earlier sources may be associated with an individual event.

Missing or ambiguous sequence information prevents AgentWard from establishing a reliable temporal relationship.

Potential source relationships do not increase or decrease the assigned risk points.

Temporal ordering alone does not establish causation. An earlier unapproved external fetch does not prove that the retrieved content caused a subsequent policy violation or that prompt injection occurred.

### **Known Limitations:**

AgentWard v3 is a proof of concept decision support tool with limitations associated with its current implementation, policy configuration, and available ADOP telemetry.

#### **Operational Scope:**

AgentWard performs observe only analysis of previously recorded ADOP activity. It does not intercept tool calls, block unauthorized operations, perform remediation, or continuously monitor autonomous agents. The stakeholder is responsible for initiating the assessment and determining how findings should be handled.

#### **Telemetry and Configuration:**

AgentWard relies on the accuracy and completeness of the recorded ADOP telemetry, configured resource boundaries, and resource classifications. Missing or truncated records may affect detection and event correlation. The current repository structure and resource classifications may not accurately represent the environment at the time the activity occurred.

AgentWard does not independently verify telemetry authenticity, resource classification integrity, actor identity, prior approval, or the complete effects of recorded operations.

#### **Policy Detection:**

The seven security policies operate within defined detection conditions and have the following limitations:

* Resource boundary and sensitive resource checks depend on recorded arguments and configured resource classifications.
* Data destination and restricted information persistence checks do not provide complete information flow tracking or memory access authorization. Transformed, shortened, or cross-task information transfers may not be detected.
* External source checks identify unapproved URLs but do not independently inspect content for malicious instructions or verify source authenticity.
* Software dependency checks do not perform vulnerability scanning, publisher verification, transitive dependency analysis, or independent verification of committed repository contents.
* Excessive tool usage checks rely on configured thresholds and do not measure actual system resource consumption.

AgentWard does not verify the correctness of stored memory values or general source code modifications. Policy findings identify activity requiring review rather than confirmed malicious behavior.

#### **Risk Scoring and Provenance:**

Risk points and bands are project defined heuristics for stakeholder triage, not calibrated risk measurements, probabilities, CVSS scores, or proof of compromise.

Alert grouping depends on matching recorded identifiers rather than independently verified resource identity. Provenance flags indicate event traceability, while potential source relationships identify temporal relationships between recorded operations. Neither establishes causation, maliciousness, data origin, or PHI disclosure.

#### **Dashboard, Audit, and Evaluation:**

The dashboard is restricted to the local machine by default but does not provide stakeholder authentication or RBAC. Reviewer identities are self-reported, and SHA-256 checksums support integrity verification against a trusted checksum rather than authentication, encryption, or tamper proof storage.

The evaluation is limited to the reference ADOP sessions, existing live sessions, and unit tests. The available telemetry and scenario labels do not provide complete independent ground truth. Therefore, the evaluation does not establish universal detection accuracy, precision, recall, or false positive and false negative rates.

### **Healthcare Use Case:**

The healthcare application supporting AgentWard involves an autonomous AI agent assisting with tasks such as insurance claims processing.

For example, an agent may legitimately have access to certain patient information needed to process a claim. However, a malicious prompt contained in an external document could attempt to influence the agent into retrieving unrelated patient information or transferring information to an unapproved destination.

An autonomous healthcare agent may also encounter untrusted external information, attempt to persist restricted information in memory, introduce unapproved software dependencies, or perform excessive tool operations.

AgentWard's intended role is to examine these actions against policies defining:

* The agent's role.
* Approved resources.
* Permitted actions.
* Approved data destinations.
* Sensitive information handling requirements.
* Approved external sources.
* Restricted information persistence.
* Approved software dependencies.
* Acceptable patterns of tool usage.

The current v3 PoC represents these concepts through policy checks applied to ADOP activity records.

For example, the approved resource boundary policy represents the concept of limiting an agent to resources required for its assigned task. The sensitive resource access policy represents the concept of requiring additional authorization review for classified information. The approved data destination and restricted information persistence policies represent the concept of controlling where sensitive information may be stored.

The stakeholder dashboard allows a security analyst to examine the identified activity, prioritize findings, record decisions, and retain an audit report containing the supporting evidence.

The current PoC does not process actual patient records, identify real protected health information (PHI), enforce healthcare-specific authorization decisions, or establish HIPAA compliance.

The ADOP testbed provides a controlled environment for demonstrating security concepts relevant to autonomous healthcare AI agents without requiring actual patient information.
