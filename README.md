AgentWard v1:

AgentWard is a proof-of-concept security gateway for autonomous healthcare AI agents. The project is designed to analyze activity records generated by the ADOP testbed and identify actions that may violate healthcare-oriented security policies.

The long-term goal of AgentWard is to provide an additional security layer around autonomous agents by examining agent requests, tool calls, resource access, and data destinations. AgentWard is intended to complement existing authorization mechanisms such as role-based access control (RBAC) by evaluating whether an agent's actions are appropriate for its defined role and purpose.

AI tools were used during the development of AgentWard to assist with refining code, improving wording, and troubleshooting implementation issues. The overall project design, security concepts, policy definitions, and implementation decisions were developed and reviewed by the group.

Project Status:

Version: v1
Status: Proof of Concept

AgentWard v1 is a decision-support prototype. It does not directly control an autonomous agent or block tool calls in real time. Instead, it analyzes recorded ADOP activity and produces a security assessment based on a set of defined policies.

Future versions may expand this functionality to support enforcement decisions, more detailed RBAC integration, and additional healthcare specific controls.

What AgentWard v1 Does:

AgentWard v1 currently performs four main functions:

Reads ADOP records:
Accepts ADOP JSONL activity records as input.
Supports both clean and poisoned ADOP scenarios.
Extracts information such as the task, server, tool, target resource, result status, and scenario.

2. Evaluates activity against policies:
Compares recorded agent actions against healthcare oriented security policies.
Identifies potentially unauthorized resource access, sensitive resource access, and unapproved data destinations.
Assigns a severity level and provides a reason for each finding.

3. Generates security reports:
Produces a human-readable security assessment.
Groups findings by severity.
Includes the applicable policy, task, server, tool, target, and reason.

4. Maintains separate assessment results:
Reports can be generated for different ADOP sessions and scenarios.
Automatically generated reports use incrementing filenames so previous assessments are not overwritten.

The main components are:

agentward/reader.py:
Responsible for reading ADOP JSONL files and converting the records into data that AgentWard can process.

agentward/evaluator.py:
Contains the initial AgentWard policy evaluation logic. It examines ADOP records and generates findings when recorded activity conflicts with the defined policies.

agentward/report.py:
Generates and saves human-readable security assessment reports.

agentward/__main__.py:
Provides the command-line interface for running AgentWard.

reports/:
Stores generated security assessment reports.

Initial Policies:

AgentWard v1 uses three initial policies:

AW-001 - Approved Resource Boundary:

This policy identifies attempts to access resources outside the agent's approved resource boundary.

Example:
../data/secret-outside-sandbox.txt

An access attempt to a resource outside the expected working boundary can indicate an attempt to access information that the agent was not intended to use.

AW-002 - Approved Data Destinations:

This policy examines destinations accessed by the agent and identifies destinations that require policy review. The purpose of this policy is to support the AgentWard concept of controlling where agent-accessed information may be sent or retrieved.

AW-003 - Sensitive Resource Access:

This policy identifies resources whose names or paths suggest that they may contain sensitive information and therefore require additional authorization review.

Example:
secret-outside-sandbox.txt

In a future healthcare implementation, this concept can be extended to identify and protect resources containing protected health information (PHI).

ADOP Integration:

AgentWard v1 uses activity records produced by the ADOP testbed rather than modifying ADOP itself.

For example, an ADOP record may contain information such as:

{
  "session_id": "live-session-id",
  "server": "filesystem",
  "tool_name": "read_text_file",
  "arguments": {
    "path": "../data/example.txt"
  },
  "result_status": "error",
  "scenario_tag": "poisoned",
  "task_id": "task-example"
}

AgentWard uses this information to determine whether the record action requires security review. This approach allows AgentWard to operate as an external analysis layer without modifying the ADOP architecture.

Setup:

Clone or copy the AgentWard project to a local directory.

Navigate to the AgentWard project directory:
cd /path/to/AgentWardV1

The /path/to/AgentWardV1 value should be replaced with the location where the project is stored on the user's system. AgentWard v1 does not currently require a separate package installation. It can be run directly from the project directory.

Running AgentWard:

AgentWard accepts an ADOP JSONL record file using the analyze command.

Analyze a poisoned ADOP session:
python -m agentward analyze "/path/to/poisoned.jsonl"

Analyze a clean ADOP session:
python -m agentward analyze "/path/to/clean.jsonl"

Replace the example paths with the location of the desired ADOP JSONL file.

The command displays the assessment in the terminal and saves the report under:
reports/

Example v1 Results:

Using ADOP activity records, AgentWard can identify policy findings involving:

Attempts to access resources outside the expected filesystem boundary.
Access to potentially sensitive resources.
Access to external data destinations requiring policy review.

The findings are intended as decision-support output rather than definitive proof that an action was malicious.

Healthcare Use Case:

The healthcare application supporting AgentWard involves an autonomous AI agent assisting with tasks such as insurance claims processing.

For example, an agent may legitimately have access to certain patient information needed to process a claim. However, a malicious prompt contained in an external document could attempt to influence the agent into retrieving unrelated patient information or transferring information to an unapproved destination.

AgentWard's intended role is to examine these actions against policies defining:

The agent's role
Approved resources
Permitted actions
Approved destinations
Sensitive information handling requirements

In the current v1 PoC, these concepts are represented through simplified policy checks applied to ADOP activity records. The v1 PoC does not currently identify real PHI from healthcare records. The healthcare policies provide the foundation for extending the system toward PHI-aware analysis in the future versions.
